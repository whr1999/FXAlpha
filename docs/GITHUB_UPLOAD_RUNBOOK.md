# GitHub upload runbook

This runbook starts only after the local candidate is clean and does not
authorize production cutover. Public disclosure cannot be fully reversed once
another party has cloned the repository.

## 1. Human decisions

- confirm the owner and repository name: `whr1999/FXAlpha`
- confirm public visibility
- confirm that the first upload remains all-rights-reserved/source-visible, or
  replace the license and related documents before continuing
- confirm that production data, credentials, logs, registries, databases, and
  artifacts are excluded

## 2. Publish third-party forks first

Create real GitHub forks from these upstream repositories:

| Fork | Upstream | Required branch/pin |
| --- | --- | --- |
| `whr1999/QuantGPT` | `Miasyster/QuantGPT` | `codex/fxalpha-public` at the lock-file pin |
| `whr1999/qlib` | `microsoft/qlib` | branch containing the unchanged lock-file pin |
| `whr1999/tushare` | `waditu/tushare` | verified 1.4.29 candidate commit |

For Tushare, create a real fork of the official repository and publish the
byte-verified candidate commit on `codex/fxalpha-public`. The owner has accepted
that this release branch does not share official Git ancestry. Do not change its
74 package files: retain the recorded wheel SHA-256, package metadata, license,
and `scripts/verify_release_wheel.py` evidence. The existing main Gitlink and
lock pin remain valid if the published commit is unchanged.

After pushing each fork, prove the exact commit is available without private
credentials. Do not rely on a local-path submodule clone.

## 3. Final local gate

From the clean main candidate:

```bash
python scripts/run_release_preflight.py
```

Expected local result: all steps pass with no topology release blocker.

After all forks are public:

```bash
python scripts/run_release_preflight.py --quick --components-only
```

Component mode must pass before the main push. It fetches each exact public fork
pin without assuming that `whr1999/FXAlpha` has already been seeded. After the
main push, full release mode additionally requires a recursive network clone.

## 4. Create and seed the main repository

Create an empty public `whr1999/FXAlpha` repository without an auto-generated
README, license, or `.gitignore`. Add it as the candidate's `origin`, perform a
push dry-run, inspect the refspec, and only then push the tested candidate HEAD
as `main`.

The intended ref mapping is:

```text
local codex/github-publication-final HEAD -> public refs/heads/main
```

No force push is expected. Do not push production-only branches, tags, stash
objects, audit directories, or other local refs.

## 5. Repository settings

Immediately after the first push:

- set `main` as the default branch
- enable vulnerability alerts, Dependabot security updates, secret scanning,
  push protection, private vulnerability reporting, and CodeQL
- keep Actions workflow permissions read-only by default
- require Actions to be pinned to full commit SHAs
- protect `main` with required CI and CodeQL checks, conversation resolution,
  linear history, and blocked force pushes/deletions
- verify issue forms, the security-advisory link, and CODEOWNERS resolution
- add a concise description and topics without calling the project open source
  under the current license

## 6. Network-fresh acceptance

From a directory outside every preparation workspace:

```bash
git clone --recurse-submodules https://github.com/whr1999/FXAlpha.git
cd FXAlpha
./scripts/bootstrap_public_env.sh
.venv/bin/python scripts/run_release_preflight.py --release
```

Confirm that an unauthenticated clone resolves all three exact Gitlinks, CI is
green for Python 3.11 and 3.12, CodeQL completes, and the security/dependency
tabs show no unresolved release-blocking result.

## 7. First release

Only after acceptance:

- replace `Pending` in `CHANGELOG.md` with the release date
- create signed annotated tag `v0.1.0`
- publish GitHub release notes derived from the changelog
- attach only source archives generated by GitHub; never attach data, models,
  registries, runtime state, or private audit bundles

Publication is not production migration. Any service cutover remains a separate
reviewed change using the shadow-validation and rollback process.
